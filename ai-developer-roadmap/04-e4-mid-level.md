# 04 · E4 Mid-level Engineer: 프로젝트를 끝까지 책임지는 사람

**핵심 질문: “목표를 받으면 방법을 정하고 출시 뒤 문제까지 처리할 수 있는가?”**

이 단계의 독립성은 도움을 받지 않는다는 뜻이 아닙니다. 필요한 결정을 내리고, 적절한 때 도움을 구하고, 출시·운영의 빈틈을 직접 찾아 메우는 능력입니다. 영상은 E3→E4 전환에서 독립적인 완수를 강조합니다. [18:22~18:54](https://www.youtube.com/watch?v=lEzkHeqd-Ck&t=1102s)

## E3와 E4의 차이

| 장면 | 작은 기능을 맡을 때 | 프로젝트를 책임질 때 |
|---|---|---|
| 요청 | 정해진 화면을 구현한다 | 필요한 화면·저장·권한·실패 흐름을 정한다 |
| 일정 | 작업 하나의 진행 상황을 알린다 | 의존 관계와 위험을 보고 범위를 조정한다 |
| 오류 | 재현하고 수정을 받는다 | 원인 가설을 세우고 확인하며 해결을 이끈다 |
| 출시 | 배포 도움을 받는다 | 확인·되돌리기·운영 담당까지 준비한다 |
| 완료 | 기능이 동작한다 | 사용자에게 전달되고 후속 문제도 정리된다 |

[Dropbox IC2](https://dropbox.github.io/dbx-career-framework/ic2_software_engineer.html)는 정의된 프로젝트의 설계·구현·출시를, [IC3](https://dropbox.github.io/dbx-career-framework/ic3_software_engineer.html)는 더 열린 문제와 여러 구성 요소에 걸친 독립적인 해결을 설명합니다. 이 자료는 그 사이의 책임 확장을 참고합니다. 번호의 대응표는 아닙니다.

## 연습 프로젝트: 소규모 모임 예약

사용자가 가능한 시간을 고르고 자신의 예약을 변경·취소하게 만듭니다. 가짜 계정과 가짜 일정으로 먼저 시험합니다. 외부 발송·실결제는 이 과제에 필요하지 않습니다.

**기능보다 먼저 정할 것**

- 한 시간대에 몇 명까지 예약할 수 있는가?
- 같은 시간에 두 사람이 마지막 자리를 누르면 어떻게 되는가?
- 예약자는 자기 예약만 볼 수 있는가? 운영자는 무엇을 볼 수 있는가?
- 통신이 끊겼을 때 성공 여부를 어떻게 알리는가?
- 삭제·취소는 어떤 기록을 남기는가?
- 장애가 나면 누가 어떤 순서로 되돌리는가?

화면의 버튼을 숨기는 것만으로 접근 권한이 지켜지지 않습니다. 실제 데이터를 주는 서버 또는 저장 서비스에서도 해당 사용자의 권한을 검사해야 합니다.

## 하나의 프로젝트를 완수하는 순서

1. **목표:** 누가 어떤 일을 끝낼 수 있어야 하는지 한 문장으로 씁니다.
2. **범위:** 이번에 하지 않을 기능까지 정해 작업의 끝을 만듭니다.
3. **구조:** 화면→요청→처리→저장의 흐름과 외부 서비스를 적습니다.
4. **작업 분할:** 먼저 예약 한 건을 끝까지 처리한 뒤 변경·취소를 더합니다.
5. **검증:** 정상, 오류, 동시 요청, 권한을 나누어 확인합니다.
6. **출시:** 실제 주소·설정·데이터·로그를 확인합니다. 내 컴퓨터의 성공과 구분합니다.
7. **복구:** 이전 코드로 되돌리는 것과 데이터 복원이 별개인지 확인합니다.
8. **사용 후 확인:** 사용자가 막힌 곳을 고치고 알려 줍니다.

## AI를 맡기는 단위도 프로젝트에 맞춥니다

한 번에 “예약 서비스를 완성해”라고 맡기면 확인할 범위가 커집니다. **목표는 전체로 공유하고 변경은 작게 검증**합니다.

```text
이 프로젝트의 목표는 예약 생성·변경·취소다.
먼저 데이터·권한·중복 예약·실패·복구 흐름을 검토해 줘.
단순한 구조를 제안하고, 대안 하나와 장단점을 비교해 줘.
작업을 나누되 각 단계가 실제로 확인 가능한 결과를 갖게 해 줘.
현재 단계의 구현과 확인을 끝낸 뒤 다음 단계로 가자.
완료 보고에는 실행한 검사와 확인하지 못한 부분을 나눠 줘.
```

사용 중인 API나 라이브러리의 동작은 공식 문서와 설치 버전에서 확인합니다. AI가 제안한 명령을 실행했다면 결과를 읽고, “성공했다”는 설명과 실제 종료·화면·저장 결과가 맞는지 봅니다.

## E4에서 필요한 기술 판단

웹 요청과 응답, 데이터 저장과 식별자, 로그인과 권한의 차이, 중복 처리 방지, 테스트, 로그, 설정 관리, 배포와 복구를 프로젝트 안에서 익힙니다. 복잡한 분산 시스템을 먼저 만들 필요는 없습니다.

오류를 고칠 때는 **재현→가설→한 가지 확인→수정→기존 동작 확인**을 반복합니다. 그때그때 AI가 권한 새 라이브러리를 넣기보다 현재 구조에서 원인을 좁힙니다.

## 남겨야 할 성과 묶음

| 자료 | 보여 주는 것 |
|---|---|
| 목표·범위·일정 한 장 | 무엇을 책임졌는가 |
| 구조·데이터 흐름 | 어떻게 동작하는가 |
| 테스트 결과 | 무엇까지 확인했는가 |
| 배포·복구 기록 | 실제 서비스에서 책임졌는가 |
| 사용자 피드백과 수정 | 전달 후에도 끝까지 챙겼는가 |

서비스가 아직 실제로 사용되지 않았다면 “운영 완료” 대신 “시험 환경에서 확인”이라고 적습니다. 이 구분 자체가 신뢰를 만듭니다.

## E4에서 오래 머무는 이유와 E5 전환

주어진 프로젝트를 빨리 끝내는 것만 반복하면 다음 문제를 정하는 경험은 늘지 않을 수 있습니다. 영상에서도 E4→E5가 가장 어려웠던 전환으로 소개되며, 제품 방향·협업·멘토링·더 긴 시야가 강조됩니다. [19:54~21:24](https://www.youtube.com/watch?v=lEzkHeqd-Ck&t=1194s)

다음 프로젝트는 요청을 받기 전에 제안해 보세요.

- 가장 자주 생기는 사용자 불편 세 가지를 모읍니다.
- 왜 지금 하나를 먼저 풀어야 하는지 비교합니다.
- 최소한의 해결 방법과 결과 측정 방법을 적습니다.
- 동료 또는 협업자에게 의견을 받고 함께 실행합니다.

**다음 레벨을 준비했다는 신호:** 프로젝트를 혼자 끝내는 데 더해 “다음에 무엇을 해야 하는가”를 근거로 설명하고, 다른 사람과 함께 성과를 냅니다.
