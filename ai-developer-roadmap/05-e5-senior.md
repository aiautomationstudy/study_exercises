# 05 · E5 Senior Engineer: 팀의 다음 문제를 정하는 사람

**핵심 질문: “누가 시키지 않아도 중요한 문제를 찾고, 팀이 해결하게 할 수 있는가?”**

E4에서 E5로의 변화는 구현 속도를 조금 더 높이는 것만으로 설명하기 어렵습니다. 프로젝트를 잘하는 사람에서 **어떤 프로젝트가 필요한지 판단하고 다른 사람도 잘하게 만드는 사람**으로 책임이 바뀝니다.

영상은 이 전환을 특히 어렵게 회고합니다. 방향 설정, 여러 역할과의 협업, 멘토링, 미래에 합류할 동료까지 생각하는 시야가 필요했다고 말합니다. [19:54~21:24](https://www.youtube.com/watch?v=lEzkHeqd-Ck&t=1194s)

## E4의 성공 방식을 확장해야 합니다

| E4에서 잘하던 방식 | E5에서 더할 행동 |
|---|---|
| 주어진 목표를 잘 완수한다 | 어떤 목표가 더 중요한지 근거를 제안한다 |
| 어려운 부분을 직접 해결한다 | 동료가 해결하도록 맥락·기준·리뷰를 제공한다 |
| 출시까지 계획한다 | 출시 뒤 유지·전환·다음 분기까지 생각한다 |
| 자신의 작업을 설명한다 | 제품·디자인·운영 담당자가 함께 결정하게 설명한다 |
| 요청받은 일을 많이 한다 | 가치가 작은 일을 줄이고 중요한 일을 선택한다 |

Senior라고 모든 기술의 전문가일 필요는 없습니다. 다만 자신의 책임 영역에서 위험한 결정을 알아보고, 모르는 것을 조사하고, 적절한 검토를 받으며, 결과를 책임질 수 있어야 합니다.

## 팀의 방향을 만드는 다섯 가지 일

1. **문제를 발견합니다.** 오류 기록, 고객 문의, 사용 관찰에서 반복되는 문제를 찾습니다.
2. **선택합니다.** 사용자 영향, 빈도, 비용, 위험을 비교해 먼저 풀 것을 정합니다.
3. **기술 방향을 설명합니다.** 단순한 해결과 더 큰 재설계의 장단점을 비교합니다.
4. **함께 실행합니다.** 동료가 맡을 수 있는 작업과 성공 기준을 만듭니다.
5. **결과로 수정합니다.** 효과가 없으면 기능을 더하는 대신 가설을 다시 봅니다.

[GitLab의 Senior Backend 기준](https://handbook.gitlab.com/handbook/engineering/careers/matrix/development/dev/backend/senior/)은 모호한 큰 문제, 복잡한 도전, 코칭·멘토링, 기술 결정과 품질을 다룹니다. [Dropbox IC4](https://dropbox.github.io/dbx-career-framework/ic4_software_engineer.html)는 팀·제품 역량·기술 시스템에 걸친 지속적 결과를 설명합니다. 여기서 제시하는 과제는 이 책임들을 AI 개발 환경에 맞춰 연습하는 제안입니다.

## 연습 프로젝트: 예약 이탈 문제를 팀 과제로 바꾸기

**가상 상황:** 예약 화면은 잘 열리지만 신청을 끝내지 않는 사람이 있습니다. “AI 추천 기능을 넣자”는 아이디어가 나옵니다.

바로 만들기 전에 다음을 확인합니다.

- 사용자가 어떤 단계에서 멈추는가?
- 그 단계가 불편한가, 일정이 없어서 나가는가, 가격을 확인하러 왔는가?
- 로그에 기록되지 않는 화면 오류나 설명의 오해가 있는가?
- 문의에서 같은 문제가 반복되는가?
- 기능 추가 없이 문구·절차를 바꿔 해결할 수 있는가?

최종 제안은 “AI 추천 기능 개발”보다 다음처럼 구체적이어야 합니다.

> 모바일에서 예약 가능한 시간이 화면 아래에 가려지는지 확인한다. 실제 사용 관찰과 기기별 오류를 보고 첫 화면을 조정한다. 완료율과 중복 예약·문의 증가 여부를 함께 본다.

이 예시는 원인을 미리 확정하지 않습니다. 관찰을 통해 가설을 확인한 뒤 바꿉니다.

## 기술 판단을 한 장에 씁니다

| 적을 것 | 예시 질문 |
|---|---|
| 문제와 근거 | 누구에게 얼마나 자주 생기는가? |
| 선택지 | 기존 구조 보완, 외부 서비스, 직접 구축 중 무엇인가? |
| 선택 이유 | 지금 규모와 팀의 운영 능력에 맞는가? |
| 비용과 위험 | 구현 시간, 월 비용, 유지 부담, 데이터 노출은? |
| 검증과 전환 | 어떤 결과면 계속하고, 실패하면 어떻게 되돌리는가? |

고급 구조를 썼다는 사실보다 **현재 문제에 맞는 선택을 했는지**가 중요합니다. 나중의 확장 가능성을 설명하되, 아직 생기지 않은 규모를 위해 복잡성을 먼저 떠안을 필요는 없습니다.

## AI를 사용해도 직접 해야 할 판단

AI는 사용자 기록의 분류, 대안 탐색, 설계 검토, 테스트 초안을 도울 수 있습니다. 실제 사용자의 경험을 대신 만들어 낼 수는 없습니다. 인터뷰를 요약하게 했다면 원문과 맞추고, 조사한 적 없는 고객의 발언을 생성해 근거로 쓰지 않습니다.

```text
다음 사용자 관찰과 오류 기록으로 문제 후보를 정리해 줘.
확인된 사실·가설·추가 확인이 필요한 것을 나눠 줘.
각 후보의 사용자 영향, 확인 비용, 기술 위험을 비교해 줘.
우리 팀이 2주 안에 확인할 수 있는 가장 작은 실험을 제안해 줘.
실제 자료에 없는 사용자 발언이나 수치는 만들지 마.
```

AI에게 “시니어처럼 판단해”라고 시키는 것과 내가 Senior의 책임을 수행하는 것은 다릅니다. 대안을 왜 선택했는지 설명하고 결과로 재검토할 수 있어야 합니다.

## 멘토링도 결과로 확인합니다

답을 빨리 알려 주는 것만이 멘토링은 아닙니다. 동료가 다음번에 더 독립적으로 판단하도록 돕습니다.

- 작업의 목적과 완료 조건을 함께 정합니다.
- 리뷰에서 수정 지시와 이유를 함께 제공합니다.
- 모르는 부분을 질문할 수 있게 합니다.
- 한 달 뒤 비슷한 일을 더 독립적으로 하는지 확인합니다.

지속적으로 내가 대신 고치고 밤에 마무리해야 한다면 팀의 능력이 커졌는지 다시 봅니다. 동료 기여를 자신의 성과로 가져오지 말고 자신의 지원과 공동 결과를 구분합니다.

## 성과 자료와 다음 레벨 준비

남길 자료는 문제 선택의 근거, 기술 결정 한 장, 동료와 나눈 책임, 사용자·팀 결과, 실패에서 바꾼 판단입니다. “회의 다섯 번”보다 어떤 결정이 가능해졌는지, “코드 리뷰 열 번”보다 무엇이 개선됐는지 씁니다.

E6를 준비할 때는 **우리 팀을 넘어선 병목 하나**를 찾습니다. 예를 들어 예약팀과 정산팀이 취소 상태를 다르게 해석해 생기는 문제입니다. 다른 팀의 우선순위를 듣고, 공통 정의를 정하고, 실제 전환을 돕는 과정을 연습합니다.

Senior에 오래 머물며 전문성을 깊게 키워도 좋습니다. E6 전환은 더 높은 타이핑 능력이 아니라 **다른 숙련자들과 경계를 넘는 성과를 만들 책임을 맡을지**의 선택입니다.
