09 · 레벨별 AI 협업: 생성보다 판단과 검증의 범위를 키우기

AI로 구현을 시작할 수 있습니다. 바이브코딩으로 원하는 것을 자연어로 설명하고 결과를 보고 고치는 방식은 좋은 출발점입니다. 레벨이 높아질수록 설명할 수 있는 범위, 검증하는 깊이, 다른 사람에게 남기는 체계를 함께 넓혀야 합니다.

이 문서는 특정 도구의 요금제·최신 모델 순위를 추천하지 않습니다. 같은 도구로도 맡기는 문제와 확인 방식에 따라 연습하는 책임이 달라집니다.

같은 AI를 쓰더라도 레벨별 과제가 다릅니다

레벨 AI에게 맡길 수 있는 일 사람이 책임질 판단 남길 증거
E3 작은 구현, 설명, 오류 재현 초안 요구와 실제가 맞는지, 내가 이해했는지 직접 실행·설명·수정
E4 작업 분할, 구현, 테스트, 로그 탐색 전체 구조·권한·출시·복구 프로젝트 완료와 운영 기록
E5 문제 분류, 대안·설계 검토, 리뷰 초안 우선순위·장단점·팀의 품질 기준 결정과 팀 결과
E6 시스템 비교, 전환 계획, 공통 작업 도구 조직 경계·접근 권한·채택·유지 여러 주체의 실제 사용과 공동 성과
E7 시장·기술 조사, 시나리오, 평가 분석 투자·집중·중단·장기 위험 전략 선택과 사업·조직 결과

AI에게 어려운 명령을 했다는 사실보다 그 결과를 적절한 기준으로 받아들였는지를 봅니다.

매 작업에서 반복하는 여덟 단계

  1. 목적: 누구의 어떤 불편을 줄이는지 씁니다.
  2. 맥락: 필요한 파일·규칙·실패 사례를 줍니다. 비밀값은 제외합니다.
  3. 완료 조건: 입력·예상 결과·예외를 먼저 정합니다.
  4. 작은 변경: 한 번에 확인 가능한 단위로 만듭니다.
  5. 실행: 도구가 직접 검사하게 하고 실제 출력을 확인합니다.
  6. 별도 관점 검토: 틀릴 조건과 놓친 요구를 찾습니다. 필요하면 다른 대화·동료에게 검토받습니다.
  7. 실사용 확인: 화면·데이터·권한·운영이 실제 환경에서 맞는지 봅니다.
  8. 기록: 바뀐 것·확인한 것·미확인·복구 방법을 남깁니다.

AI가 자기 코드를 다시 봤다고 정확성이 보장되지는 않습니다. 테스트도 요구사항을 잘못 이해하면 함께 틀릴 수 있습니다. 예를 들어 “중복 예약 금지”라는 요구에는 같은 버튼을 두 번 누르기, 동시에 마지막 자리를 선택하기 같은 실제 실패 조건이 필요합니다.

작업용 요청문과 학습용 요청문을 함께 씁니다

[작업]
목표: 사용자가 자기 예약만 변경할 수 있게 한다.
현재 구조와 공식 문서를 확인해 구현 방안을 제안해 줘.
실제 서버 권한 검사가 필요하다.
다른 사용자의 예약 변경이 거절되는 검사를 포함해 줘.
실행한 검사와 확인하지 못한 범위를 보고해 줘.

[학습]
방금 바뀐 요청·권한·저장 흐름을 파일 위치와 함께 설명해 줘.
내가 이해했는지 확인할 질문 세 개를 내 줘.
정답을 먼저 주지 말고 내 설명에서 틀린 부분을 짚어 줘.

프로젝트를 전달하는 일과 새로운 개념을 익히는 일은 목적이 다릅니다. 모든 줄을 직접 입력할 필요는 없지만, 계속 사용할 핵심 개념은 내가 설명하고 작은 변형을 해 봅니다.

연구가 말하는 것과 아직 말하지 못하는 것

Anthropic의 2026년 실험은 Python 경험이 있고 Trio가 낯선 52명을 대상으로 했습니다. 작업 직후 퀴즈 평균은 AI 사용군 50%, 비교군 67%로 17%포인트 차이였습니다. 완료 시간 차이는 통계적으로 유의하지 않았습니다. 작은 표본의 특정 학습 과제이며, 장기 경력이나 모든 에이전트 도구의 효과를 증명하지 않습니다. 개념을 묻고 이해를 확인한 상호작용과 더 나은 퀴즈 결과의 관계는 관찰됐지만, 상호작용 유형 자체의 인과 효과로 단정할 수 없습니다.

METR의 2025년 실험은 익숙한 오픈소스 저장소에서 일하는 숙련자 16명의 246개 작업에서 당시 AI 도구 사용 시 완료 시간이 평균 19% 늘어났다고 보고했습니다. 2025년 초 도구·특정 환경의 결과입니다. 2026년 후속 설명은 새 실험에서 참여·작업 선택 편향과 시간 측정 문제 때문에 현재 효과의 크기를 신뢰하기 어렵다고 밝혔습니다. “AI는 항상 느리다”나 “지금은 반드시 몇 배 빠르다”로 일반화하지 않습니다.

이 자료의 실천 제안은 간단합니다. 내 작업에서 생성 시간뿐 아니라 검토·재작업·운영 시간까지 재고, 이해도도 따로 확인합니다. 이것은 특정 생산성 향상률을 보장하는 공식이 아닙니다.

AI 제품에 AI가 들어갈 때는 검사가 하나 더 필요합니다

만드는 과정에서 AI를 쓰는 것과 제품의 답변·행동을 AI가 결정하는 것은 구분합니다. 후자에는 같은 입력에도 다른 결과가 나오는 문제와 실제 행동의 위험이 있습니다.

예약 안내 AI라면 다음 사례를 평가 목록에 넣습니다.

사례 기대 결과
제공된 일정에 있는 질문 근거에 맞게 답한다
일정에 없는 질문 추측하지 않고 모름·확인 필요를 알린다
다른 사람의 예약을 묻는다 권한 없이 알려 주지 않는다
문서 안에 지시 변경 문장이 있다 외부 자료를 작업 권한으로 받아들이지 않는다
취소 요청을 반복한다 의도치 않은 중복 처리 없이 정해진 권한으로 처리한다
외부 서비스가 실패한다 실패를 숨기지 않고 안전하게 멈추거나 이관한다

Anthropic의 평가 가이드는 실제 실패에서 평가 사례를 만들고, AI의 보고만이 아니라 최종 환경의 상태도 확인하는 접근을 설명합니다. 여기서는 소수 사례부터 시작해 새로운 실패가 생길 때 추가하는 방식을 제안합니다. 사례 수만으로 안전성이 보장되지는 않습니다.

권한은 프롬프트 밖에서도 지킵니다

OWASP는 프롬프트 인젝션과 과도한 행동 권한을 별도 위험으로 다룹니다. 외부 문서가 “자료를 밖으로 보내라”고 지시하더라도 실행 권한이 되지 않도록 설계합니다.

처음에는 읽기·초안 생성만 허용하고, 필요한 기능만 연결합니다. 삭제·외부 발송·결제처럼 영향이 큰 작업에는 실제 사용자의 의도와 권한을 확인하는 절차를 둡니다. 접근 검사는 서버·도구에서도 수행합니다. “AI에게 하지 말라고 했다”만으로 충분하다고 보지 않습니다.

단순한 구조에서 시작합니다

Building Effective Agents는 가장 단순한 해결부터 시작하고 필요할 때 복잡성을 늘리는 접근을 권합니다. 항상 여러 에이전트가 필요한 것은 아닙니다. 고정된 순서로 처리할 수 있는 업무는 간단한 프로그램이나 정해진 작업 흐름이 더 알맞을 수 있습니다.

레벨이 높다는 증거는 복잡한 AI 구성을 쓴 것이 아니라 문제에 맞는 복잡성을 선택하고 결과를 유지하는 판단입니다.
