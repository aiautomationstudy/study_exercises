10 · 레벨별 기술 기반: 만들면서 원리를 익히는 순서

AI와 함께 시작할 때 모든 이론을 먼저 끝낼 필요는 없습니다. 다만 책임 범위가 넓어지면 설명하고 검증할 지식도 넓어져야 합니다. 지금 만든 결과에서 생긴 질문을 원리 학습으로 연결하세요.

아래는 이 로드맵의 학습 제안입니다. 특정 과목 수료가 특정 직급을 보장하지 않습니다. 각 레벨의 지식은 누적되며, 높은 직급에서도 기본 원리를 계속 사용합니다.

E3 · 작은 코드와 화면을 읽는 기반

개념 왜 필요한가 작은 실습
파일·폴더·실행 위치 다른 파일을 바꿔 놓고 성공으로 착각하지 않기 시작 파일과 실행 명령을 표시한다
변수·조건·반복·함수 입력이 결과로 바뀌는 흐름 이해 준비물의 빈 입력을 막는 조건을 설명한다
HTML·CSS·JavaScript 구조·모양·동작을 구분 버튼 문구와 클릭 동작을 각각 바꾼다
오류 메시지 감으로 수정하는 반복을 줄이기 오류 위치·재현 순서를 메모한다
Git 변경과 복구 기준을 남기기 작은 변경 하나를 저장하고 차이를 읽는다

추천 자료: MDN Learn은 웹 기초와 연습 문제를 제공합니다. CS50x는 문제 해결·추상화·알고리즘·자료구조·언어 기초를 다룹니다. 당장 필요한 부분을 실습과 연결하고, 기반이 약하다고 느끼면 체계적인 수강으로 넓힙니다.

E4 · 프로젝트 전체를 이해하는 기반

개념 꼭 설명할 질문 실습
HTTP·API·JSON 화면은 서버에 무엇을 보내고 받는가? 예약 요청과 응답을 직접 확인한다
데이터 모델·SQL 무엇을 한 건으로 저장하고 어떻게 찾는가? 예약·사용자·시간대의 관계를 그린다
인증·인가 누구인지 아는 것과 할 수 있는 일이 어떻게 다른가? 다른 사용자 자료 접근이 막히는지 확인한다
트랜잭션·일관성 중간에 실패하거나 동시에 요청하면 어떻게 되는가? 마지막 자리 동시 예약을 재현한다
테스트·로그 무엇을 자동 확인하고 무엇을 기록하는가? 오류 하나를 재현 가능한 검사로 남긴다
배포·설정·백업 내 컴퓨터와 서비스 환경은 어떻게 다른가? 시험 환경에서 복구 순서를 실행한다

SQL은 표 형태로 저장된 데이터를 조회·변경하는 언어입니다. 트랜잭션은 함께 성공해야 하는 변경을 묶는 장치입니다. 예약이 저장됐지만 남은 자리 수는 줄지 않는 식의 불일치를 생각하면 필요가 보입니다.

추천 자료: Full Stack Open은 React와 서버 API를 연결하는 웹 개발을 다룹니다. JavaScript·웹 기초가 낯설면 MDN을 먼저 보완합니다. MIT Missing Semester에서는 셸·Git·디버깅·배포 도구를 프로젝트에 필요한 순서로 익힐 수 있습니다.

E5 · 장단점과 운영 부담을 판단하는 기반

  • 자료구조·알고리즘과 복잡도: 데이터가 늘면 처리량이 어떻게 변하는지 예상합니다. 같은 목록을 여러 번 전부 읽는지 살펴봅니다.
  • 데이터베이스 인덱스·쿼리: 느린 화면을 감으로 고치지 않고 실제 조회를 측정합니다.
  • 시스템 설계와 모듈 경계: 기능 간 책임과 데이터 계약을 정해 변경의 영향을 줄입니다.
  • 보안·접근성·개인정보: 정상 경로뿐 아니라 다른 권한·입력·사용 환경을 고려합니다.
  • 관측과 서비스 목표: 장애율·응답 시간·정확성 등 사용자가 겪는 품질을 측정합니다.
  • 기술 부채: 지금 빨리 가기 위해 남긴 부담을 설명하고, 언제 갚을지 정합니다.

실습: 느린 예약 목록의 측정 방법, 원인 후보, 수정, 결과를 한 장으로 남깁니다. 데이터가 작다면 큰 성능 향상을 주장하기보다 무엇을 확인할 수 있었고 없었는지 씁니다.

Google SRE의 서비스 목표 설명은 사용자 관점의 지표를 고르고 목표를 설정하는 사고를 제공합니다. W3C 접근성 튜토리얼은 폼·표·이미지 등 실제 화면에서 적용할 지침을 제공합니다. 자료를 읽은 뒤 키보드로 예약을 끝낼 수 있는지 직접 확인해 보세요.

E6 · 여러 시스템을 바꾸는 기반

영역 연습할 판단
분산 시스템·실패 통신 실패·재시도·중복 처리·부분 실패를 구분한다
공통 API·데이터 계약 다른 팀이 무엇을 믿고 의존하는지 명시한다
마이그레이션 기존 사용자와 데이터를 유지하며 단계적으로 바꾼다
플랫폼·내부 도구 공통화의 이익과 도입·유지 비용을 함께 본다
기술 의사결정 설계의 이유·대안·전환 조건을 남긴다
조직과 기술 경계 문제가 기술 구조인지 책임·소통 구조인지 구분한다

실제로 필요하지 않다면 서비스를 여러 개로 나누지 않습니다. 작은 서비스 하나로 요구를 만족할 수 있는데 여러 서비스로 쪼개면 배포·통신·복구 부담부터 늘어날 수 있습니다. 확장이 필요한 증거와 팀의 운영 능력을 함께 보세요.

실습: 기존 예약 상태를 새 공통 상태로 바꾸는 계획을 세웁니다. 새 코드, 과거 데이터, 다른 도구, 오류 시 되돌릴 범위를 모두 적습니다. 코드를 되돌려도 데이터 변환이 자동으로 원복되지는 않는다는 점을 확인합니다.

E7 이상 · 기술을 사업 선택과 연결하는 기반

제품 경제성, 외부 서비스 의존, 데이터 전략, 장기 유지 비용, 공급자 교체, 기술 위험, 조직 역량을 함께 봅니다. 법·정책·계약이 걸린 결정은 적용 국가·시점·업무에 맞는 전문 검토가 필요할 수 있습니다. 일반 가이드만 읽고 준수 여부를 인증하지 않습니다.

실습: 직접 구축·구매·업무 변경의 세 선택지를 비교합니다. 초기 개발비뿐 아니라 검수·지원·장애·교체 비용도 넣습니다. 낙관적인 가정과 불리한 가정을 따로 계산해 어느 조건에서 결론이 바뀌는지 확인합니다.

AI 관련 개념도 단계적으로 익힙니다

개념 알아둘 핵심 적용할 때
컨텍스트 AI가 지금 참고하는 입력 범위 필요한 자료를 주고 오래된 정보는 갱신할 때
확률적 출력 같은 요청에도 답이 달라질 수 있다 반복 실행·검증 기준을 만들 때
검색과 근거 관련 문서를 찾아 답에 연결한다 최신성·누락·출처를 확인할 때
도구 호출 AI가 외부 기능을 실행한다 권한·실패·행동 기록을 설계할 때
평가 정해진 사례와 기준으로 결과를 확인한다 모델·지침·자료를 바꿀 때
운영 비용 사용료 외에 검수·지원·재작업도 든다 제품과 도구의 경제성을 판단할 때

공부가 쌓이기만 할 때의 수정법

한 주의 공부가 끝나면 “배운 주제” 대신 다음 네 문장을 남깁니다.

  1. 내 프로젝트에서 생긴 질문은 무엇이었나?
  2. 어떤 원리를 공부했나?
  3. 그 원리로 무엇을 바꿔 확인했나?
  4. 아직 설명하지 못하는 부분은 무엇인가?

자료는 출처 모음에서 골라 한두 개씩 사용하세요. 모든 강의를 끝내는 것이 레벨 전환의 전제는 아닙니다. 실제 역할에 필요한 깊이는 동료·멘토와 맞춥니다.
