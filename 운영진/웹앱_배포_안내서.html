운영진을 위한 웹앱 배포 안내서

Codex·Claude Code와 함께, 만든 앱을 실제 주소로 열고 고치고 되돌리기

코드는 AI와 함께 만들 수 있는데, “이제 어디에 올리지?”, “주소는 어떻게 붙이지?”, “잘못 올리면 어떻게 되돌리지?”에서 막힌 적이 있나요?

이 안내서는 Codex·Claude Code를 이미 사용하지만 개발·운영 경험은 짧은 운영진을 위한 자료입니다. AI에게 파일 작업과 확인을 맡기고, 여러분은 대상 앱과 공개 범위, 실제 동작을 판단합니다. 서버의 보안·업데이트·백업 기반은 개발자가 관리합니다.

기본 경로는 Dokploy입니다. Dokploy는 내 서버의 앱을 웹 화면에서 배포하고 관리하는 도구입니다. 개발자가 다른 도구를 이미 준비했다면 도구 비교를 먼저 읽고, 팀의 실제 절차를 따르세요. 이 문서를 읽었다고 우리 팀 서버에 Dokploy가 설치되거나 계정이 발급되는 것은 아닙니다.

이번에 끝낼 일

작은 안내 앱 하나를 로컬에서 확인하고 → GitHub에 보관하고 → 팀이 준비한 서버에 배포하고 → HTTPS 주소로 열고 → 문구를 고쳐 다시 배포하고 → 이전 버전으로 되돌리는 연습까지 합니다.

첫 실습에는 실제 참가자 정보·결제·메일 발송·운영 DB를 넣지 않습니다. 서버 설치 실습은 아닙니다. 서버 준비가 끝나지 않았다면 4단계까지 진행하고, 준비된 뒤 5단계부터 이어 가세요.

기준일: 2026년 10월 30일. 메뉴 이름은 설치 버전에 따라 조금 다를 수 있습니다. 못 찾겠으면 현재 화면을 AI와 확인하세요. 없는 버튼을 추측해서 누르지 않습니다.

먼저, 내 상황에서 시작할 곳 찾기

내 상태 시작할 곳
앱도 없고 배포 화면도 없다 0~4단계로 앱과 저장소를 준비하고, 서버 관리자에게 준비 요청을 보냅니다.
앱은 있지만 배포 화면 주소·계정이 없다 0단계에서 준비 요청을 하고, 1단계에서 앱을 점검합니다.
배포 화면과 계정을 받았다 1단계부터 시작합니다.
이미 배포한 앱을 고치고 싶다 8단계로 갑니다. 기존 배포 경로를 먼저 확인합니다.
배포 뒤 문제가 생겼다 9단계와 「막혔을 때」를 봅니다.
오늘 하던 일을 새 대화에서 이어 가고 싶다 10단계의 재개 요청문을 보냅니다.

따라 하는 방법: 아래 요청문은 내 컴퓨터에서 해당 앱 폴더를 연 Codex 또는 Claude Code의 대화창에 보냅니다. 브라우저 주소창이나 Dokploy의 환경변수 칸에 붙여넣지 않습니다. 한 요청문을 통째로 보내고, 각 단계의 확인할 것을 직접 본 뒤 다음으로 갑니다.

AI에게 브라우저 작업을 맡길 때는 팀이 준비한 Aside 연결을 이용하세요. 연결되지 않았다면 안내된 버튼을 직접 눌러도 됩니다. AI가 만든 코드의 반복 화면 시험은 별도 자동 시험으로 할 수 있습니다. 계정 로그인·MFA는 필요한 본인 확인만 직접 진행합니다.

배포에서 헷갈리기 쉬운 여섯 가지

이름 이번 실습에서 하는 역할
로컬 실행 내 컴퓨터에서 앱을 켜 보고 고칩니다. 내 컴퓨터를 끄면 이 실행도 멈춥니다.
GitHub 저장소 앱의 코드와 수정 이력을 보관합니다. 코드를 올렸다는 것만으로 서비스가 바뀌지는 않습니다.
빌드 코드를 실제 실행할 형태로 만듭니다. 문법·설정·의존성 문제로 이 단계에서 실패할 수 있습니다.
배포 서버에서 새 버전을 실행하게 바꿉니다. 서버의 앱을 바꾸는 작업입니다.
도메인·DNS 사람이 읽는 주소와 그 주소가 찾아갈 서버를 연결합니다. 앱 화면에서 주소를 등록하는 것과 DNS 레코드를 만드는 것은 별도일 수 있습니다.
HTTPS 브라우저와 서버 사이의 연결을 암호화합니다. 주소가 열리는 것과 올바른 인증서로 안전하게 열리는 것을 함께 확인합니다.

이번 안내서를 읽는 GitHub Pages와, 앞으로 배포할 앱의 서버는 용도가 다릅니다. GitHub Pages는 HTML·CSS·브라우저 JavaScript 같은 정적 파일을 제공합니다. 로그인 처리·공용 DB 조회처럼 서버에서 실행할 코드가 있는 앱은 별도의 실행 환경이 필요합니다. 정적으로 내보낸 웹앱은 Pages에 올릴 수도 있으므로, 내 앱에 서버 실행이 필요한지 AI에게 먼저 확인하게 합니다.

설치·계정 발급을 제외한 소형 앱 실습에 2~3시간을 계획용 예상 시간으로 잡으세요. 실제 측정한 소요 시간은 아닙니다. 앱의 상태와 빌드 속도에 따라 달라집니다.

0단계. 서버 관리자에게 준비받기

꼭 할 것

팀의 서버 관리자에게 아래 요청문을 전달하세요. 이미 준비돼 있다면 새 설치를 요청하지 말고 기존 주소와 운영 규칙을 받으면 됩니다.

해당 앱 폴더의 Codex·Claude Code 대화에 보내세요
운영진이 Codex·Claude Code로 만든 작은 웹앱을 직접 배포하는 연습을 하려고 합니다.
서버 보안·업데이트·백업은 개발자가 관리하고, 저는 담당 앱의 생성·배포·주소 연결·상태 확인·이전 버전 배포를 맡으려 합니다.

다음을 준비하거나 기존 정보를 알려 주세요.
1. 팀의 배포 관리 화면 주소와 제 개인 계정, 담당 프로젝트.
2. 사용할 앱 템플릿, GitHub 조직·저장소 규칙, 배포할 브랜치와 빌드 방식.
3. 앱 주소를 만들 수 있는 도메인 영역과 이름 규칙, HTTPS 준비 여부.
4. 앱 내부 포트, 상태 확인 경로, 자원 제한과 동시 빌드 기준.
5. 이전 버전 이미지 보관과 실제 복구 방법, 제 계정의 허용 작업.
6. DB·업로드가 있는 앱이라면 전용 접속 계정, 저장 위치, 원격 백업과 복원 담당.

첫 연습은 실제 개인정보·결제·메일 발송·운영 DB 없이 하겠습니다.
기존 서버의 웹 포트와 다른 서비스에 영향을 주지 않는 연습 환경을 부탁드립니다.
비밀번호·토큰은 공용 채팅에 쓰지 말고 팀이 정한 비밀 관리 방법으로 전달해 주세요.

개발자는 최초에 GitHub와 배포 도구 연결, 계정 권한, DNS·인증서, 자원 제한, 백업과 복구를 준비합니다. 운영진에게 서버 전체 관리자 계정을 공유하는 것으로 대신하지 않습니다. 기본 권한으로 원하는 제한을 만들 수 없다면 별도 프로젝트·실행 환경 또는 제한된 배포 화면을 개발자가 준비합니다.

확인할 것: 내 계정으로 관리 화면에 들어가 담당 프로젝트를 볼 수 있고, 사용할 주소 규칙과 복구 방법을 알고 있습니다. 다른 앱을 고치거나 서버 설정을 다룰 필요는 없습니다.

아직 준비되지 않았다면

1~4단계는 내 컴퓨터에서 진행할 수 있습니다. 운영 서버에서 인터넷의 설치 명령을 그대로 실행하거나, 이미 사용 중인 웹서버를 중지하지 않습니다. Dokploy 기본 설치는 80·443·3000 포트를 요구하므로 기존 서비스와의 공존은 개발자가 먼저 설계해야 합니다. 설치 요구 사항

1단계. AI에게 현재 상태부터 확인시키기

기존 앱이 있으면 그 앱 폴더를 엽니다. 새 앱을 만들면 빈 실습 폴더를 열고 시작하세요. 팀의 실제 서비스 폴더에서 연습 앱을 덮어 만들지 않습니다.

해당 앱 폴더의 Codex·Claude Code 대화에 보내세요
이 폴더의 웹앱을 팀 서버에 배포하려고 해. 먼저 읽기 전용으로 상태를 확인해 줘.

- 실제 폴더 경로와 Git 저장소·브랜치·미커밋 변경을 확인해 줘.
- 앱의 기술, 실행·빌드 방법, 서버 실행 필요 여부, DB와 업로드 사용 여부를 알려 줘.
- 이미 배포 중이라면 실제 배포 경로를 찾아 줘. 기존 스크립트와 새 배포 도구가 같은 앱을 동시에 배포하게 만들지 마.
- 환경변수는 이름과 필요 시점만 확인하고 비밀값은 출력하지 마.
- 아직 앱이 없는 빈 폴더라면 그 사실을 알려 줘.

이번 작업의 진행 기록은 이 앱 폴더의 배포기록.md에 남겨 줘.
관리 화면 주소·저장소·브랜치·앱 이름·배포 주소·내부 포트·현재 단계·검증 결과·다음 행동을 기록하되, 비밀번호·토큰·개인정보는 적지 마.
지금은 코드·운영 설정·DNS를 바꾸거나 배포하지 마.

확인할 것: AI가 내가 의도한 폴더와 앱을 설명합니다. 배포기록.md에는 모르는 항목이 미확인으로 남아 있습니다. 주소나 포트를 AI가 임의로 지어내 채우지 않았는지 보세요. 이 기록은 로컬 또는 팀의 비공개 저장소에서 관리합니다.

2단계. DB 없는 작은 안내 앱으로 시작하기

처음에는 운영진 연습 안내 페이지를 만듭니다. 기능이 단순해야 배포 문제와 앱 기능 문제를 구분하기 쉽습니다. 기존 앱을 배포한다면 새로 만들지 말고 3단계로 갑니다.

해당 앱 폴더의 Codex·Claude Code 대화에 보내세요
이 빈 실습 폴더에 운영진 연습 안내 앱을 만들어 줘.
팀의 앱 템플릿이 있으면 그것을 우선 사용하고, 없으면 팀에서 지원하는 Next.js 기반으로 작게 구성해 줘.

첫 화면에는 제목 '운영진 배포 연습', 안내 항목 3개, 눈에 보이는 '연습 버전 1' 문구를 넣어 줘.
새로고침해도 열리고 휴대폰 너비에서 읽기 편하게 만들어 줘.
상태 확인용 /health 경로는 정상일 때 HTTP 200을 반환하게 해 줘.
DB·로그인·파일 업로드·결제·외부 메시지 발송·유료 API는 넣지 마.

직접 로컬에서 실행하고 기본 화면과 /health를 확인해 줘.
실행한 명령과 결과, 내가 열어 볼 로컬 주소를 배포기록.md에 남겨 줘.
기존 파일이 있는 폴더라면 덮어쓰지 말고 먼저 별도 실습 폴더인지 확인해 줘.
서버 배포와 GitHub 공개는 아직 하지 마.

직접 확인할 것: AI가 알려 준 로컬 주소에서 제목·안내 3개·연습 버전 1이 보입니다. 휴대폰 모양의 좁은 화면에서도 읽을 수 있습니다. /health에 접속하면 간단한 정상 응답이 나옵니다. 아직 다른 사람에게 줄 운영 주소는 아닙니다.

3단계. 서버에서 실행할 준비하기

6단계. 환경설정과 HTTPS 주소 연결하기

먼저 환경변수 확인

환경변수는 실행할 앱에 전달하는 설정입니다. 사이트 주소처럼 공개돼도 되는 값과 DB 접속 비밀번호처럼 숨겨야 하는 값이 섞일 수 있습니다.

  • Environment(환경설정)에서 앱에 필요한 값만 설정합니다. 첫 연습 앱은 외부 서비스 비밀키가 없어도 동작하도록 준비합니다.
  • 빌드할 때 필요한 값인지, 서버 실행 때 필요한 값인지 AI에게 구분하게 합니다. Dockerfile 빌드의 비밀은 전용 Build-time Secrets 등 팀의 방법을 씁니다.
  • NEXT_PUBLIC_처럼 브라우저에 포함되는 설정에 비밀키를 넣지 않습니다.
  • 비밀값은 팀의 비밀 관리 방식이나 해당 도구의 비밀 입력란으로 전달하고, 대화·공유 문서·화면 캡처에 넣지 않습니다.

회사에서 제공한 주소 붙이기

관리자가 허용한 이름을 받습니다. 아래 guide.apps.example.com은 설명용 예시입니다. 그대로 사용할 수 있는 주소가 아닙니다.

  1. Domains → Add Domain을 엽니다.
  2. Host에 관리자가 허용한 내 앱 주소를 넣습니다. Host에는 보통 https://를 빼고 이름만 적습니다.
  3. 앱 내부 포트는 배포기록.md의 값을 사용합니다. 정적 웹서버와 Next.js 서버의 포트가 항상 같지는 않습니다.
  4. 첫 실습의 경로는 /로 두고, 별도 지시가 없으면 Internal Path·Strip Path·Custom Entrypoint를 바꾸지 않습니다.
  5. 관리자가 정한 방식으로 HTTPS를 켜고 인증서 설정을 선택한 뒤 저장합니다.

회사 앱 영역 전체에 대한 wildcard DNS가 준비돼 있으면 새 이름마다 DNS를 직접 만들 필요가 줄어듭니다. 그래도 해당 앱의 도메인 경로 등록은 필요합니다. wildcard DNS와 HTTPS 인증서는 별도 준비 사항입니다. 준비됐는지는 0단계에서 확인합니다.

일반 Application의 도메인 경로는 저장 후 적용되지만, Docker Compose의 도메인 변경은 재배포가 필요합니다. 환경변수·코드 변경의 반영 여부도 별도로 확인하세요. 도메인 설정

9단계. 이전 버전으로 되돌리는 연습

롤백(rollback)은 이미 보관된 이전 실행 버전을 다시 배포하는 작업입니다. 연습 버전 2에서 버전 1로 돌아가 보겠습니다.

먼저 알아둘 두 가지

  1. 이전 버전 이미지가 보관돼 있어야 합니다. Dokploy의 특정 과거 버전 복구는 레지스트리 연결과 Rollback 설정이 필요합니다. 버튼이 없거나 이전 이미지가 없으면 개발자가 준비한 코드 재배포 절차를 사용합니다.
  2. 코드 복구는 DB 복원이 아닙니다. 환경변수·업로드 파일·DB 구조와 데이터가 함께 과거로 돌아간다고 생각하면 안 됩니다. 이번 실습은 DB가 없어 이 차이를 안전하게 연습할 수 있습니다.

화면에서 할 일

  1. Deployments에서 기록해 둔 연습 버전 1을 찾습니다.
  2. 개발자가 복구 가능하다고 확인한 버전의 Rollback을 실행합니다.
  3. 새 배포 작업이 끝나면 실제 주소에서 연습 버전 1이 보이고 /health가 정상인지 봅니다.
  4. 코드 저장소와 서버 상태를 맞춥니다. 이미지 복구만 하면 GitHub에는 버전 2가 그대로 있을 수 있습니다.

  1. 연결할 정확한 주소를 정합니다. 예: service.example.com.

  • [ ] 이전 버전 복구를 수행하고 GitHub와 서버의 현재 상태를 맞췄습니다.
  • [ ] 비밀값과 개인정보가 코드·공유 기록·화면 캡처에 들어가지 않았습니다.
  • [ ] 자동 배포가 언제 실행되는지 알고 있습니다.
  • [ ] 배포기록.md가 있어 다른 AI 대화나 다음 담당자가 이어받을 수 있습니다.
  • [ ] DB·업로드를 추가했다면 재배포 후 유지와 접근 권한까지 확인했습니다.

팀에 결과를 공유할 때는 앱의 용도, 허용된 서비스 주소, 확인한 기능, 현재 버전, 남은 문제를 적으세요. 관리 화면 로그인 주소·계정·DB 접속정보·비밀 설정은 공개 게시판에 올리지 않습니다.
